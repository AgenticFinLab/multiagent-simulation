# 09 · 状态、提交与恢复

[返回总览](README.md) · 前一篇：[执行与规模](08-execution-and-scaling.md) · 下一篇：[使用与观测](10-operation-and-observability.md)

## 1. 持久化路线

PostgreSQL 保存版本化状态和事务记录，BlobStore 保存 checkpoint、大型输入输出及其他不可变载荷。先持久化载荷，再在数据库事务中提交引用。

选择事务存储，是为了把主体变化、环境后果、活动接续和后续事件放在同一生效位置。数据库提供原子性；运行所有权、尝试有效性和跨对象关系仍由应用协议实现。[PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)

| 记录 | 必要内容 | 用途 |
|---|---|---|
| runs | run_id、定义摘要、当前版本、owner_epoch、运行状态 | 所有权与最近生效位置 |
| state_versions | 主体、环境、活动的版本记录或内容引用 | 固定版本读取与恢复 |
| phases / tasks | 坐标、读版本、触发事件、任务清单、输入引用 | 重启后重建完整阶段 |
| attempts / candidates | 尝试身份、有效性、结果摘要、载荷引用 | 选择有效候选，排除迟到结果 |
| requests / deliveries | 请求、待响应关系、消息与消费身份 | 等待、响应关联和投递去重 |
| commits / events | 提交摘要、更新、后续事件和派发状态 | 确认效果及重新派发 |
| calls / reservations | 外部调用、用量预留、实际用量和未知状态 | 费用归因与配额恢复 |
| blobs | 内容摘要、大小、格式与可达引用 | 跨 worker 装载和完整性校验 |

这是逻辑记录设计，最终表结构在实现里确定。恢复所需关系完整保存，不以诊断采样代替。

## 2. 固定版本读取

SnapshotView 按 state_version 读取主体和环境，活动会话加载对应的 continuation_ref。任务在派发前保存其输入引用与读取依据，候选生成期间不读取最新可变状态。

可用版本化行、不可变快照与增量组合实现该接口；参考实现首先采用数据库版本记录和不可变内容引用。不能用一份只保留最新值的表冒充过去的读取版本。

在途任务、待接续活动和保留回放记录引用的状态均为回收根。只有不再被这些对象及保留策略引用的候选载荷，才可作为孤立内容回收。

## 3. 一次阶段提交

1. **登记计划。** 固定 phase_id、读版本、到期事件和任务清单，持久化后再派发。正常派发与重启派发使用同一逻辑任务身份。
2. **保存候选。** worker 将完整结果与 checkpoint 持久化，返回摘要和引用；协调进程核对身份与完整性，登记候选。
3. **计算后果。** 收齐有效结果后，形成环境、活动、主体与消息计划；解释过程不产生未登记外部效果。
4. **事务生效。** 锁定或条件更新 run 记录，检查 owner_epoch、expected_version、任务清单和 selected_attempts；写状态、请求处置、投递、后续事件与 commit 记录。
5. **继续执行。** 提交成功后返回 CommitReceipt，从已提交事件安排后续派发。

数据库以 `(run_id, commit_id)`、逻辑投递身份等唯一约束防止重复生效。相同 commit_id 再提交时，内容摘要一致则返回已有回执；不一致则报告冲突。

过程记录与状态在同一提交中保存必要关联。运行指标可以稍后补发；指标服务故障不能使已生效后果失去恢复依据。

## 4. 所有权与重试

每个 run 有一个有效协调所有者。重建时通过数据库协议取得新 owner_epoch；旧代次即使恢复连接，也无法再提交新状态或派发有效任务。

每个 task_id 至多选中一个有效 attempt。未提交的旧尝试结果进入无效记录，不改变模拟状态。已完整持久化的候选可以经过核对后接纳，不必一律重新计算；接纳决定持久保存。

如果外部调用需要重做，记录新的 call_id 及其关联。系统保证已提交的逻辑效果去重，外部 API 调用本身可能重复并产生不同响应或费用。

Ray 的进程重启与方法重试服从上述身份协议。不能让框架自动重试绕过 ModelAccess、候选选择和效果去重。

## 5. 故障恢复矩阵

| 中断位置 | 恢复动作 | 必须检查 |
|---|---|---|
| 计划已登记、任务未派发 | 从任务表补派发 | 输入与读版本未变 |
| worker 执行中、结果未保存 | 核对外部调用后重试有效任务 | 旧尝试失效，未知调用有账目 |
| Blob 已写、候选未登记 | 核对可识别结果，或重算后回收孤立载荷 | 无未提交内容进入视图 |
| 候选已登记、提交前 | 复用完整候选，重新构造同一后果计划 | 必需任务齐全，版本与所有者有效 |
| 事务已提交、回执丢失 | 按 commit_id 查询回执 | 内容相同，不重复生效 |
| 提交后、后续派发前 | 从事件表继续派发 | 消息及任务去重 |
| 活动等待中重启 | 装载已提交 checkpoint 和等待关系 | 仅在正确坐标提供对应响应 |
| 旧协调实例继续运行 | 数据库拒绝旧代次写入 | 不产生第二条提交序列 |

事务状态确认后才能确定恢复位置。单独找到一个 MAF checkpoint、一个日志文件或最后轮数，均不足以确认整个 run 的状态。

## 6. MAF 接续状态的一致性

活动提交同时保存 template_version、continuation_ref、成员版本、会话完整性摘要和 pending_request_ids。恢复时检查这些记录与 checkpoint 一致，再向工作流提供已到达的响应。

MAF 中间产生的 checkpoint 属于候选执行记录。只有 RunStore 指向的已提交引用才是活动的生效接续位置。流程结构、executor 身份、序列化格式和依赖版本必须可重建。

会话恢复校验失败时停止该接续，不使用空会话继续模拟。模板升级需要明确迁移；当前没有自动恢复到新版本图的兼容承诺。具体桥接合同见 [06](06-activities-and-workflows.md#bridge)。

## 7. 暂停、预算阻塞与结束

| 操作或状态 | 行为 |
|---|---|
| 正常暂停 | 优先完成当前阶段提交，停止进入下一阶段 |
| 部分阶段暂停 | 预算或故障使当前阶段不能完成时，保存任务及候选，保持读版本 |
| 恢复 | 核对状态、版本、调用账目与接续引用，继续未完成任务 |
| 强制停止 | 失效在途尝试，按故障恢复规则保留可解释状态 |
| quiescent | 当前无可推进事件，仍存在等待或允许的外部输入 |
| completed | 达到模型终止条件，必需清理与记录已提交 |

部分阶段暂停不提交“已经完成的一半主体”。预算补足后可以继续同一任务清单；有效候选复用，尚未完成任务仍读取原版本。长期保留任务输入是支持这种恢复的必要成本。

操作不会悄悄替换模型、改变超时含义或填充默认行动。修改模型需建立新运行定义；兼容的执行资源调整则记录新的运行配置版本。

## 8. 恢复与回放分别检查什么

恢复验证中断后能够继续已承诺的状态序列。记录回放读取初始状态、提交变化和保存的外部响应，用于重建状态、检查因果与后果；重算验证则再次执行确定性组件进行比较。

回放不重新发起真实外部副作用。不可查询的外部效果保持未知，不能通过重新打印日志宣布恢复成功。实际科学复现和领域有效性需要另行设计研究证据。
