# 07 · 模拟时间与通信

[返回总览](README.md) · 前一篇：[活动与 MAF](06-activities-and-workflows.md) · 下一篇：[执行与规模](08-execution-and-scaling.md)

## 1. 时间合同

参考实现采用**离散事件队列 + 同一时刻内的有序阶段**。模拟坐标为 `(t, p)`：t 为整数时间单位，p 为该时刻的因果阶段。周期行为通过定时事件表达。

这个选择统一承载主体激活、消息到达、环境定时变化和活动继续，适合稀疏激活及跨时刻等待。密集模型仍需处理全部活跃对象，队列本身不保证比整轮遍历更快。

| 规则 | 含义 |
|---|---|
| 阶段固定读版本 | 本阶段所有任务读取同一 state_version |
| 结果统一处理 | 必需结果到齐后，按声明规则形成一次阶段提交 |
| 即时效果后续可见 | 当前提交产生的即时反馈最早在 `(t, p+1)` 消费 |
| 延迟效果未来可见 | 延迟 d > 0 时安排到未来 t，具体阶段按事件规则确定 |
| 顺序与物理执行分离 | 事件身份及模型优先级决定逻辑处理顺序 |
| 没有隐式时间跳跃 | 无新事件时按等待或完成条件处置 |

MAF superstep、模型请求耗时和模拟坐标各有含义。增加内部推理步骤会增加运行成本；只有行为或环境声明相应持续时间时，才增加模拟时长。

## 2. 事件与阶段怎样衔接

事件信封包含 event_id、kind、target、coord、source_id、payload_ref。排序键采用坐标、模型声明的事件优先级和稳定身份，不能采用 worker 返回时间。

到期消息在其可见坐标进入本次输入，基础状态仍取固定版本；其消费记录随阶段提交。环境到期事件在后果处理中改变状态，依赖该变化的主体反应安排到后续阶段。

例如模型要求“t=5 的资源到期释放先于主体行动”，则将释放安排在 `(5,0)`，相应主体激活在后续阶段。若二者被刻意安排在同一阶段，主体读取释放前状态，环境按已声明的同阶段规则处理请求。装配检查与示例应使这种先后关系可见。

每个阶段执行：

1. 选取最早到期事件，固定 state_version 与任务清单。
2. 合并同一独立主体或同一活动的到期触发，构造输入和接续响应。
3. 有界派发函数与 MAF 任务，收集本阶段有效候选。
4. 处理环境、活动和主体更新，生成投递与后续事件。
5. 原子提交后推进；失败时保留当前阶段以便恢复。

采用保守屏障保证观察与生效关系清楚。活动等待未来模拟事件时可释放 worker；本阶段仍在进行的模型计算会延迟该阶段提交。这是当前路线的明确代价。

## 3. 消息的逻辑语义

| 字段 | 作用 |
|---|---|
| message_id、correlation_id | 稳定身份及对邀请、申请或问答的关联 |
| sender、recipient、activity_id? | 通信身份及局部活动范围 |
| sent_at、visible_at | 发送和允许接收的模拟坐标 |
| content_ref、schema_version | 不可变内容与类型 |
| delivery_policy | 可靠投递、模型化丢失、期限与成员资格规则 |

同一内容发给多人时，可以共享载荷，每名接收者仍有独立 delivery_id。物理传输重试以 delivery_id 去重；若模型需要丢包或重复通信，则由通信组件生成显式的模拟结果。

默认在发送提交时解析接收者，保存接收集合；到达时检查主体状态及模板声明的成员资格要求。发送者后续改变订阅关系不会改写已提交的历史接收集合。

兴趣路由、邻接边和组织汇总可作为通信组件。索引只加速已声明的路由；改变谁能收到消息、让代表者代收或替换成摘要，属于模型配置变化。

## 4. 等待、超时与外部输入

| 情况 | 处理 |
|---|---|
| 等待未来消息或时刻 | 提交等待索引及接续引用，调度其他就绪工作 |
| 同一坐标有多个匹配响应 | 按稳定顺序合并，模板声明 any / all 消费方式 |
| 模拟期限到达 | 产生模型定义的超时响应或后果 |
| API 超时 / 配额不足 | 运行层有限重试或暂停，默认不改变模拟决策 |
| 没有事件但仍有等待 | 标记 quiescent 并报告等待图和可注入输入 |
| 即时反馈无限循环 | 达到阶段上限后暂停，保留因果链 |

外部人工输入或远端服务结果需要显式指定注入坐标并保存内容。运行模式若采用墙钟期限决定结果，必须把这种依赖写入模型定义；事后对记录排序不足以消除它对决策的影响。

默认同坐标的有效答复先满足对应等待，再处理其期限事件；其他边界规则由 TimePolicy 显式定义。等待完成、取消或成员退出后，迟到响应保留处置记录，不重新唤醒已结束路径。

等待环是诊断线索。有未来定时事件或允许的外部输入时，环未必是死锁；系统报告实际未满足条件，不擅自取消活动。

## 5. 随机性与受控回放

初始化、主体行为、环境和消息机制使用相互独立的随机流。种子从 run_seed、组件版本、逻辑任务或事件身份派生，重试复用同一逻辑流。

运行时不让并发任务共享可变全局随机数发生器。记录回放使用已保存的外部响应；真实模型重新调用可能给出不同结果，不承诺逐字复现。

对确定性行为或固定响应，改变 worker、批量和完成顺序，应保持已提交状态和逻辑事件关系。若模型本身声明墙钟输入或执行布局相关行为，这一性质需要按其合同另行界定。

## 6. 贯穿示例：A 同时参加 X 和 Y

| 坐标示意 | 活动 X：A、B、C | 活动 Y：A、D | 系统处理 |
|---|---|---|---|
| t=0 | A 提出方案，等待 B、C | 尚未开始 | 保存 X 请求、消息与 checkpoint |
| t=1 | B、C 的答复到达，继续协商 | A 接受 D 邀请 | 分别构造视图，持久登记两项活动 |
| t=2，同一阶段 | X 申请 A 的资源 | Y 也申请该资源 | 二者读取同一版本，由环境统一分配 |
| t=2，后续阶段 | 收到接受或拒绝反馈 | 收到相应反馈并继续 | 对应 checkpoint 接续，避免重复占用 |
| t=3 | 修改方案、结束或继续等待 | 完成或取消 | 生命周期更新后主体 A 继续存在 |

该表省略部分 p 阶段。工程用例通过固定响应分别构造 X 成功、Y 成功、双方撤回和延迟等分支，验证流程能表达不同后果。行为机制决定实际走哪条路径。
