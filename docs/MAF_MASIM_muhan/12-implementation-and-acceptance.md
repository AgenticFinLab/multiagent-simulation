# 12 · 实施计划与验收

[返回总览](README.md) · 前一篇：[迁移与工程](11-migration-and-engineering.md) · [决策与待确认项](decisions.md)

本篇规定实现顺序。最终能力由 [01](01-scope-and-requirements.md) 定义，架构与合同由 02–10 定义。早期缩小的是用例和工作量，后续阶段仍须完成持续活动、重叠参与、分布式执行及恢复。

各里程碑均为待实施和验收的目标，完成状态以对应的测试与负载报告为依据。

## 1. 里程碑

| 阶段 | 交付 | 通过条件 | 未通过时的处理 |
|---|---|---|---|
| M0 · 设计与实施范围确认 | 确认合同、首轮负载、资源和依赖核验范围 | 关键职责、状态归属和反馈边界无冲突；明确实施范围 | 修改所属设计，保留未决项 |
| M1 · 骨架与高风险探针 | 新仓库骨架；真实 MAF 请求—检查点—新实例接续；事务和 Blob 最小链路 | 会话、请求、成员身份与版本完整恢复；候选引用可区分 | 修正 MAF 适配或持久合同，暂不扩大负载 |
| M2 · 完整基本运行 | 群体初始化、事件、函数与 MAF、环境、单阶段提交、过程记录 | 行动有后果和反馈；重复请求不重复生效；新增组件不改通用循环 | 定位合同或职责缺口 |
| M3 · 持续与重叠活动 | 活动成员、等待索引、模拟定时、重叠参与与共享状态处置 | X / Y 覆盖成功、拒绝、取消、退出及延迟；等待释放 worker | 修正活动、消息或环境语义 |
| M4 · 共享执行与故障恢复 | Ray 池、端点总配额、运行所有权、部分阶段暂停和恢复 | 多 worker 与乱序返回满足受控一致性；故障矩阵通过 | 在失败层修正，保留可复现输入 |
| M5 · 工程交付与负载报告 | 使用文档、扩展示例、指标、负载与限制报告 | 干净环境可复现工程用例；R1–R8 有证据；规模报告完整 | 明确剩余能力，不能以目录齐全宣布交付 |

M1 专门验证会改变整个架构判断的机制，使用小型合成组件即可。M2 尽早建立端到端链路。M3–M4 完成终态中的复杂活动与可靠运行，M5 再整理交付与容量结论。

## 2. 终态需求与验收对应

| 需求 | 关键验收 | 最晚形成证据 |
|---|---|---|
| R1 持续主体与群体 | 稳定生成、跨活动保留、停用清理、稀疏激活 | M2 / M5 |
| R2 异质行为 | 函数、LLM、混合、工具及内部角色共用合同 | M3 |
| R3 环境与行动 | 新操作接入、灵活参数、联合后果、失败反馈 | M2 / M3 |
| R4 持续活动 | 跨实例、跨时刻恢复及动态成员 | M3 |
| R5 重叠与时间 | 同一主体双活动、可见时间、资源竞争、等待环 | M3 / M4 |
| R6 执行与成本 | 有界派发、端点总配额、预算阻塞、规模分解 | M4 / M5 |
| R7 一致恢复 | 计划、候选、提交、派发各位置故障 | M4 |
| R8 操作与检查 | 状态查询、暂停恢复、因果定位、回放与导出 | M5 |

## 3. 必须包含的实质测试

| 测试 | 构造与断言 |
|---|---|
| 跨 worker 接续 | 工作流发出多个请求，保存 checkpoint，在新进程提供部分及全部响应；成员会话和未完成请求正确 |
| 私有信息范围 | 为 A、B 和 X、Y 各放不同标记；检查实际模型输入、工具读取及接续上下文 |
| 活动动态成员 | 在等待边界加入、退出成员；旧响应按规则处置，固定图可恢复 |
| 同主体资源竞争 | X、Y 同阶段申请同一份资源；最多按资源规则分配，不因返回顺序改变结果 |
| 组合操作 | 加入活动和预约资源声明为同一组；任一前提失败时无部分成功，相关主体更新按实际处置应用 |
| 失败反馈 | 请求被拒绝后继续修改、退出或等待；记录拒绝且不写入虚假的成功状态 |
| 消息与期限 | 延迟消息到期才可见；deadline 与 API timeout 分别触发；重复投递只消费一次 |
| 不完整结果 | 并发分支中一支失败或尚未结束，不提交已经流出的半份结果 |
| 故障与旧实例 | 在提交前后中断，恢复期间旧 worker / coordinator 返回；只有有效结果生效 |
| 预算中途耗尽 | 部分候选完成后暂停；补足预算恢复同一输入版本，已完成候选不无故重算 |
| 状态重建 | 初始状态加提交记录重建终态，与在线状态一致 |
| 执行布局变化 | 固定响应和逻辑随机流，改变 worker、批量和返回顺序，比较状态及事件关系 |
| 组件扩展 | 增加一种行为、环境能力和活动模板，通用协调循环保持不变 |

测试需要跨边界检查下一次输入、持久记录和恢复结果。仅验证类型名称、方法存在、返回非空或进程能启动，无法覆盖这些性质。

## 4. 三类工程负载

下表为建议的测量输入，数值待 M0 结合资源确认，尚不是已达到的规模或真实模型预算。

| 负载 | 起始与扩展配置 | 重点测量 |
|---|---|---|
| 持续主体与稀疏激活 | N = 100、1,000、10,000；1% / 10% 活跃率 | 状态容量、热内存、激活定位、装载与派发 |
| 局部复杂协作 | 100 个主体；10–100 项未结束活动；每项 2–5 人，含重叠成员 | checkpoint 体积、等待成本、会话隔离、接续延迟 |
| 共享环境高争用 | 100–1,000 个活跃主体竞争一组资源，加入延迟、重复和中断 | 后果处理、事务吞吐、尾延迟及恢复 |

为每类负载提供函数行为与模拟模型响应版本。用真实 MAF 运行受控响应，检验实际框架接续和开销；真实端点探针单独报告模型、凭据配置方式、调用量和预算。

不使用受控响应的吞吐推断真实模型吞吐，也不使用“注册了多少主体”代替复杂活动并发能力。

## 5. 每次验收保留什么

- 源码提交、依赖锁、模型与执行配置、初始状态摘要。
- 硬件、worker、并发、状态与消息大小、响应分布、故障注入位置。
- 测试断言、原始结果、提交与调用关联，失败时的可重现输入。
- 通过项、未覆盖项、已知限制及其影响。
- 容量、吞吐、成本、延迟分解与恢复结果，分别呈现。

修改了核心合同、依赖或失败路径后重跑受影响验证。没有新变化或未解决问题时，无须为了增加测试数量反复执行同一检查。

## 6. 完成条件与范围控制

基础设施交付要求 R1–R8 的验收都有证据，工程示例可由另一位开发者独立运行，新增组件有公开合同和示例，恢复与规模限制可解释。

任一关键性质失败时，停止对应阶段的扩量或交付判断，保留小型失败用例；其他独立工作可以继续。阶段产物不以测试总数、文档长度或接通某个模型 API 作为替代。

领域环境扩展、真实事件研究、EPG 领域转换、多租户平台及新的高性能时间算法后续单独规划。
