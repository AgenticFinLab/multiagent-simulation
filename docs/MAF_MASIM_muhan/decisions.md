# 设计决策与待确认项

[返回总览](README.md) · [实施与验收](12-implementation-and-acceptance.md)

本页汇总设计目标、技术选择、待确定的实施条件及需要原型验证的问题。

## 1. 设计目标

| 编号 | 方向 |
|---|---|
| G1 | 先建设兼顾规模、灵活性与运行有效性的模拟基础设施，领域实验随后推进 |
| G2 | 大量主体持续存在，多种局部活动按需发生 |
| G3 | 活动可以跨模拟时刻持续，同一主体可以参加多个未结束活动 |
| G4 | 充分利用 MAF 的行为、工作流和运行支撑能力 |
| G5 | MASim 按需要迁移和发展适用资产，不要求保留完整旧框架 |
| G6 | 主体能够形成不同提议和行动路径，模型可以使用声明假设与合成配置 |
| G7 | 以完整运行链路验证基础设施能力，原型逐步扩展到终态 |

## 2. 本稿采用的技术路线

| 编号 | 选择 | 依据与代价 | 主文档 |
|---|---|---|---|
| D1 | 持久主体状态与共享 worker 分离 | 分别管理主体容量与计算量；增加装载和序列化 | [08](08-execution-and-scaling.md) |
| D2 | 函数与 MAF 共用行为接口，按计算需要组合 | 简单行为保持低开销，复杂行为复用 MAF；需维护适配合同 | [04](04-agents-and-memory.md) |
| D3 | 主体与角色保留长期状态，行为实例统一记录独立和活动流程的局部进度 | 支持持续等待和重叠参与；需维护统一恢复入口 | [06](06-activities-and-workflows.md) |
| D4 | 离散事件、有序阶段、保守屏障 | 观察和后果清楚；慢任务限制阶段推进 | [07](07-time-and-communication.md) |
| D5 | ResolutionCoordinator 先联合处置，各模块据同一结果生成更新计划 | 组合失败与重新分配有明确顺序；处理器及全局热点需验证 | [05](05-environment-and-actions.md) |
| D6 | Python + Ray + PostgreSQL + BlobStore | 复用执行经验并验证联合提交；增加部署成本 | [08](08-execution-and-scaling.md)、[09](09-state-and-recovery.md) |
| D7 | 每 run 一个逻辑提交所有者，任务与尝试分别记录 | 限制重复效果与旧实例写入；单 run 提交上限需测量 | [09](09-state-and-recovery.md) |
| D8 | 行为、子角色和机制调用共用端点总配额与独立账目 | 约束全局使用量并避免重复归因；unknown 需要核对 | [08](08-execution-and-scaling.md) |
| D9 | 记忆、工具、聚合和混合行为显式配置 | 保留模型灵活性；需区分执行优化与模型变化 | [04](04-agents-and-memory.md)、[08](08-execution-and-scaling.md) |
| D10 | 先完整保留恢复依据，诊断允许采样 | 支持恢复与过程核对；持久 I/O 成本需报告 | [10](10-operation-and-observability.md) |
| D11 | 接续时配对原 checkpoint 与当前输入，由 Bridge 处理反馈和可见信息 | 避免旧观察与重复接续；需逐调用检查上下文 | [06](06-activities-and-workflows.md) |
| D12 | 输入准备、行为与环境辅助计算共用执行和恢复协议 | 记忆和环境模型计算有明确依赖；增加阶段任务记录 | [07](07-time-and-communication.md)、[09](09-state-and-recovery.md) |
| D13 | ModelBinding 属于模型定义，EndpointBinding 属于执行配置 | 区分模型变化与部署调整；未知 revision 的同一性证据有限 | [08](08-execution-and-scaling.md) |
| D14 | 主体结构与行为机制分别配置，复合主体支持持久角色、有界嵌套和受控角色变化 | 保留跨任务经验，局部会话按实例隔离；增加状态与计算成本 | [04](04-agents-and-memory.md)、[06](06-activities-and-workflows.md) |

各项选择共同构成参考架构，其关键前提及验证方式见第 4 节。

## 3. 待确定的实施条件

| 问题 | 本稿建议 | 决定的内容 |
|---|---|---|
| 首轮验收重点是什么？ | 同时覆盖稀疏持续主体、重叠活动、高争用环境三类工程负载 | 原型优先级和资源分配 |
| 首轮规模阈值怎样确定？ | 在保守推进与单 run 提交路线下，按可用硬件确认容量、吞吐及恢复阈值 | M0 的资源与测量配置 |
| 首版外部能力到什么深度？ | 完成 MAF、只读/计算工具、模拟效果与协议扩展合同；完整 A2A、复杂界面和外部写操作随后安排 | 避免首版同时承担平台化工作 |

实施前需确定计算资源、模型端点及调用预算；数值目标结合工程负载制定。

## 4. 需要原型回答的技术问题

| 风险 | 需要的证据 | 验证失败后的边界 |
|---|---|---|
| MAF 跨实例状态不完整 | 独立及活动实例、多请求、嵌套角色与真实 Agent 会话接续 | 修正适配层，不能用空会话继续 |
| 动态成员或角色难以保持图与请求一致 | 加入、停用、同名重建、迟到响应和取消测试 | 调整数据绑定与序列化协议 |
| 当前视图未正确进入恢复流程 | 部分反馈恢复后检查实际模型提示与工具读取 | 修正 Bridge 和上下文装配 |
| 组合失败留下错误占用 | 加入+预约失败后，后续申请获得正确资源 | 修正联合处理器，停止相关后果提交 |
| 机制任务恢复更换上游结果 | 摘要完成后中断，恢复复用封存结果和依赖 | 修正阶段封存协议 |
| 同名端点改变实际模型 | 模型、解码和已知 revision 变化测试 | 拒绝静默继续，记录不可核对项 |
| 阶段屏障限制吞吐 | 分解慢调用、排队与空闲时间 | 保持行为配置，优化已测明的瓶颈 |
| 单次提交或环境热点过重 | 高争用负载的后果处理与事务指标 | 先优化对应路径，再评估需要新时间机制 |
| 配额与未知调用恢复不清楚 | 丢失响应、服务重建、重复尝试测试 | 保留 unknown 状态并暂停核对 |
| 状态与 checkpoint 体积失控 | 长活动、长记忆及恢复保留期测量 | 调整保留和装载方式，信息压缩另记模型变化 |
