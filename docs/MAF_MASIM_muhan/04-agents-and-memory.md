# 04 · 主体、行为与记忆

[返回总览](README.md) · 前一篇：[模型与合同](03-model-and-contracts.md) · 下一篇：[环境与行动](05-environment-and-actions.md)

## 1. 主体怎样定义和长期存在

主体定义包括身份与角色、可变化属性、行为实现、记忆规则、关系和生命周期。初始化可以来自显式配置，也可以来自群体分布。运行中的主体状态保存于 RunStore，只有被激活时才装载所需部分。

主体数量因此不要求与 Python 对象、Ray Actor 或模型会话数量一一对应。活动结束释放的是局部执行资源；主体身份、可保留记忆和关系继续存在。

主体停用时，模型应明确是否保留其资源、如何处理在途消息、是否取消所参与活动。系统保存这些处置，防止留下无法唤醒的等待关系。

## 2. 行为的统一接入

采用 FunctionExecutor 与 MAFExecutor 两类适配器，统一接收 ExecutionRequest、返回 SegmentResult。具体行为以配置组合，避免为每种行为名称建立一套独立调度体系。

| 行为形态 | 执行方式 | 适用情况 |
|---|---|---|
| 数值或规则行为 | 普通函数、显式状态机 | 高频更新、清晰规则、轻量决策 |
| LLM 行为 | MAF Agent + 结构化结果 | 需要理解文本、比较方案和生成提议 |
| 规则与 LLM 混合 | 函数与 Agent 节点组合 | 规则给出约束或候选，模型负责其中声明的判断 |
| 检索增强行为 | MAF Agent + 范围受控的检索工具 | 需要从主体记忆或模型允许的资料中选择上下文 |
| 内部多角色行为 | MAF Workflow 组合分析、计划、检查等角色 | 一个主体内部进行复杂任务分解 |
| 多主体活动 | 独立活动 + MAF WorkflowBridge | 多名模拟参与者沟通、协商和合作 |

规则可以限制合法参数，也可以决定何时请求模型。混合策略必须声明执行顺序和失败行为；系统预算不足不会自动将一个 LLM 主体改成规则主体。

同一种 ActorDefinition 可以绑定不同 BehaviorDefinition，便于替换机制。替换后形成新的模型配置，系统保存机制版本并用相同合同接入。

## 3. 内部角色、组织和活动分别怎样表达

| 对象 | 是否有独立模拟身份 | 状态与通信 |
|---|---|---|
| 主体内部的分析助手 | 通常没有 | 使用该主体授权的输入，在片段内形成建议 |
| 世界中独立存在的组织成员 | 有 | 独立 ActorState、记忆与信息权限 |
| 组织或群体关系 | 由模型声明 | 关系模块维护成员、角色、代表权与可见范围 |
| 一次协商或协作 | 独立 activity_id | 保存本次参与者、局部记录和流程进度 |

例如，A 内部的计划与检查角色可以共享 A 的输入；A 与 B 的协商必须走已声明的主体通信。若使用“主持人”，需要说明它是可信流程控制代码、模拟中的独立主体，还是某主体内部助手。它获得的信息由这个身份决定。

组织可以有领导者和下属，也可以没有层级。层级属于模型组件，不能从物理 worker 的上下级关系自动推导。代表者是否能替成员作决定、成员是否直接行动，需要在组织权限和行为定义中说明。

## 4. 记忆、会话和活动记录

| 内容 | 归属与持久方式 | 更新时点 |
|---|---|---|
| 主体长期记忆 | ActorState 的版本化记忆引用 | 提交时按主体规则追加或更新 |
| 活动共享记录 | ActivityState 关联内容 | 消息或活动操作生效后 |
| 成员私有会话 | 按 run / activity / actor 隔离 | 随活动检查点提交 |
| 独立行为会话 | 按 run / actor / behavior 隔离 | 随独立任务结果提交引用 |
| 临时推理与工具中间值 | 当前执行片段 | 默认暂态；需要保留时按显式规则归档 |

MAF 提供 Session 和 Context Provider 等上下文构件；适配层负责将它们对应到模拟身份及状态版本。[MAF 会话与记忆](https://learn.microsoft.com/en-us/agent-framework/concepts/agents/conversations/)

同一活动的成员会话由其 checkpoint 保存，RunStore 保存生效引用；同一份会话只有一个恢复来源。独立主体在一个阶段的多条触发合并成一次独立行为任务，避免并发改写其独立会话。

同一主体参加 X、Y 时，两份成员会话可以并存。它在 X 获得的信息何时进入长期记忆、何时可被 Y 读到，由 MemoryPolicy 决定；其他成员的私有信息不会因为共享 activity_id 而变成公共资料。

## 5. 可见输入怎样构造

ObservationBuilder 在固定读取版本下，为每个参与者生成 ActorView：

1. 读取其身份、可见属性和环境投影。
2. 取出在当前坐标已经到达、且允许该主体接收的消息与反馈。
3. 按记忆规则检索可用内容，记录选择依据和结果引用。
4. 提供该主体允许了解的环境能力、活动角色和工具描述。
5. 将视图交给对应行为；MAF 上下文只装配这份视图及其合法接续状态。

记忆检索、摘要和反思作为可替换组件。摘要会影响后续输入，因此保存原始引用、生成版本和所用模型。不得将“系统已经记录”直接等同于“所有主体均可见”。

记忆、检索、反思与规划的分工可参考 Generative Agents；具体机制与参数仍由模型作者选择，其研究结果不直接证明本系统中主体的行为有效性。[Generative Agents 论文](https://arxiv.org/html/2304.03442v2)

## 6. 灵活行为需要怎样的运行支持

LLM 可以选择行动对象、参数、顺序、沟通内容、等待和合作方式，也可以形成多步计划。环境允许的操作、主体能力与资源限制共同决定可执行范围，详见 [05](05-environment-and-actions.md)。

当后续判断依赖其他主体答复或环境效果时，行为返回模拟边界；得到已生效反馈后再继续。仅依赖本次已知信息的内部计算可以在一个片段内完成。

工具、记忆和行动能力由模型组件配置。工程验证使用受控组件检查其组合行为，包括不同会话、行动选择及反馈路径。
