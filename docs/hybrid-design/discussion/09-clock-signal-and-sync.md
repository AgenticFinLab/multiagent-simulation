# 09 · 时钟、信号与同步策略（平台只定义机制，不替使用者决定策略）

> 回应“异步/陈旧意图不符合真实场景、平台不该替使用者决定”：**平台定义「时钟 + 信号 + 同步策略接口」即可；具体“等待 / 异步 / 陈旧容忍”是使用者配置的策略。**

## 1. 一句话原则

**平台提供“机制”，使用者决定“策略”。**

- 平台：定义**时钟（Clock）**、**信号（Signal）**、**同步策略接口（SynchronizationPolicy）**。
- 使用者：决定“要不要等、等多久、超时怎么办、某个 agent 要不要用旧意图”——这些都是**可配置的策略**，不是平台写死的默认行为。

## 2. 平台定义的三样东西

### 2.1 时钟（Clock）—— 平台自建
- 只定义**逻辑时间**：`round / level / step`。
- 只负责“按什么顺序推进”，**不规定“每轮必须等谁”**。

### 2.2 信号（Signal）—— 平台自建
- 激活信号：`ActivationSignal(round, level, agent_id, reason, budget, deadline)`。
- 时钟/同步信号：`BarrierOpen / BarrierClose / DeadlineReached` 等，用于通知“这一层/这一轮到了什么状态”。
- 平台只定义信号格式与发送时机，**不规定 agent 收到后必须怎么做**。

### 2.3 同步策略接口（SynchronizationPolicy）—— 平台自建接口，策略可插拔
- 平台只定义接口：`should_wait(round, level, pending) -> wait | proceed`。
- 给一个**最简单默认实现**，其余由使用者替换：

| 策略 | 行为 | 谁决定 |
|------|------|--------|
| `strict`（默认） | 等本层所有 agent 完成才进下一层 | 平台默认 |
| `deadline` | 等到截止时间，超时的 agent 走 fallback | 使用者配置 |
| `nonblocking` | 不等待，未完成的后续补交 | 使用者配置 |

## 3. 这样“等待/异步”就不再是平台问题

- **“该不该等”** → 由 `SynchronizationPolicy` 决定，默认严格等待（最符合可复现）。
- **“某个 agent 要不要异步、要不要用旧意图”** → 由使用者在 agent 层自己实现（例如用“低频激活 + 规则执行”），平台不管。
- 之前“异步刷新 / 陈旧意图”的说法，降级为**一种使用者可选的 agent 策略**，不再作为平台设计的一部分。

## 4. 修正后的时间语义（最终版）

```text
平台（机制）：
  Clock       —— 逻辑时间 round/level/step
  Signal      —— ActivationSignal / Barrier / Deadline
  SyncPolicy  —— 接口 + 默认 strict（可插拔）

使用者（策略）：
  某个 agent 每几轮决策一次、要不要异步、超时怎么办、旧意图能不能用
```

**一句话：平台造“钟表、信号灯、排队规则接口”；使用者决定“谁几点来、排多久、超时怎么办”。**
