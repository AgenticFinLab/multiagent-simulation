# 02 · 关键问题与瓶颈

> 约定：本文先“列全”，再“分清我们能解决 vs 不解决”。**大模型底层推理/服务加速（自研 serving、GPU kernel、投机解码等）不在本设计范围内**——我们把 LLM 视为一个黑盒端点，拥有 `latency / throughput / rate-limit / cost` 四个外部属性，我们只在其**上**做架构。

## 1. 瓶颈全景图

| # | 瓶颈 | 表现 | 属于 |
|---|------|------|------|
| B1 | LLM 吞吐/延迟/成本 | 全量 LLM 决策时，调用数/秒与 token 数爆炸 | 我们解决（调度、批处理、缓存、降级） |
| B2 | 通信爆炸 | 点对点消息 O(N²)，广播风暴 | 我们解决（分层 hub、兴趣路由、压缩） |
| B3 | 状态与内存 | 每 agent 状态 × N；记忆膨胀 | 我们解决（冷热分层、压缩、外部存储） |
| B4 | 时序与一致性 | LLM 延迟差异导致乱序；撮合需要严格顺序 | 我们解决（逻辑时钟、层级屏障、异步预取） |
| B5 | 调度与并行 | 微秒级规则与秒级 LLM 混跑，互拖后腿 | 我们解决（引擎分离、流水线、慢路径隔离） |
| B6 | 可靠性与恢复 | 长跑中途失败、重复投递、状态漂移 | 我们解决（checkpoint、幂等、resume） |
| B7 | 可观测与治理 | 10⁵ agent 无法逐一看，需聚合与溯源 | 我们解决（分层指标、采样 trace、成本归因） |
| B8 | 多租户/隔离/安全 | 会话串扰、权限越界、成本失控 | 我们解决（隔离键、配额、命名空间） |
| B9 | 配置与场景工程 | 10⁵ agent 的 persona/参数如何生成 | 我们解决（程序化生成、模板、分层 persona） |
| B10 | LLM 推理加速 | 单次推理太慢、GPU 不够 | **不解决**（黑盒假设） |

## 2. 逐一分析（我们解决的部分）

### B1 决策吞吐与成本

这是**第一瓶颈**。本质不是“单次 LLM 慢”，而是“调用次数太多”。

- 每轮决策总数若等于 N，N=10⁵ 时每轮 10⁵ 次调用不可行。
- 缓解思路（详见 `09`）：
  1. **只让少数 agent 真正调 LLM**（活跃子集/抽样/重要性采样）；
  2. **分层聚合**：leader 代表一组 agent 做 LLM 决策，成员用规则跟随；
  3. **批处理 + 异步预取**：把决策与执行解耦，利用等待时间；
  4. **三级缓存**：prompt 前缀缓存（共享 persona/system 前缀）、语义缓存（相似状态去重）、结果缓存（相同输入同输出）——已有数据表明三者结合可省 60–70% 调用成本；
  5. **降级链**：预算/延迟超限时 LLM→RuleLLM→Rule。

### B2 通信爆炸

全对全点对点消息是 O(N²)。在 10⁵ 规模下不可行。

- 本质缓解：**让消息走“拓扑 + hub + 兴趣路由”**，而不是全连接。
- 市场交互天然扇入（所有交易者→市场），没问题；**难的是意见/信号传播**。
- 手段：
  1. 显式有向拓扑（MASim `topology.yml` 已有）；
  2. 分组 leader 聚合（组内 O(k²) + 组间 O(m²)，k、m ≪ N）；
  3. 兴趣订阅（类似 OASIS 用推荐系统作为信息 hub）；
  4. 消息压缩（摘要/向量/引用，只传引用不传全文）；
  5. 广播降级为“摘要广播 + 按需拉取”。

### B3 状态与内存

10⁵ agent 即便每个只 10KB 状态也是 1GB 量级，长期记忆/历史更甚。

- 冷热分层：热（actor 内存，仓位/现金/短期记忆）、温（本地 KV/文件，逐轮记录）、冷（对象存储/向量库，长期记忆/知识/快照）。
- 复合 agent 的状态是其子状态 + 自身状态，**不要重复存储子状态全文**，存引用或摘要。
- 记忆压缩：只保留影响决策的摘要与关键事件（参考生成式 agent 的记忆-反思机制）。

### B4 时序与一致性

规则 agent 微秒级、LLM agent 秒级，若同步等待会把整轮拖到最慢者。

- 用**同步屏障 + 异步预取**：世界推进仍按同步轮次（可复现），但 LLM 决策在上一轮就开始预取（投机执行）。
- 市场撮合需要严格顺序：用**逻辑时钟 + 层级 + 时间戳**；同一市场内按确定性顺序撮合（同 seed 可复现）。
- LLM 结果乱序到达：给每个决策挂 `(round, level, agent_id, seq)` 标签，超时/乱序按策略丢弃或降级。

### B5 调度与并行

异构执行时长混在一起会互相拖累（Amdahl 定律：一个慢任务串行部分拖垮整体）。

- **引擎分离**：规则引擎（同步、快、在 actor 内）与 LLM 引擎（异步、慢、走 worker 池 + 队列）分开。
- **流水线**：observe → enqueue LLM → 等待期间做规则决策 → 汇聚。
- **慢路径隔离**：个别超时 LLM 不得阻塞其他 agent（每 agent/组有超时与降级）。
- 借鉴 Matrix：**无状态 worker 从队列拉任务**，与有状态 actor 解耦，可提升吞吐 2–15×。

### B6 可靠性与恢复

几十万 agent、长跑多轮，中途失败不可避免。

- 轮级 checkpoint（MASim 已有 `detect_resume_round` + `write_resume_checkpoint`）。
- 幂等投递：消息带 seq，重复投递不重复消费。
- 状态快照：actor 状态可序列化/恢复；resume 时从快照重建。
- 明确“可恢复的粒度”：至少轮级；理想是 level 级或 sub-agent 级（成本更高）。

### B7 可观测与治理

- 分层指标：agent 级 → group 级 → 场景级，逐层聚合。
- 采样溯源：全量记录决策 I/O 太贵，按重要性采样记录 trace。
- 成本归因：每 agent/组 token 消耗、缓存命中率、降级次数。
- 借用 MAF：OpenTelemetry span/event/metric + 中间件插桩。

### B8 多租户/隔离/安全

- 同一集群跑多个实验/租户：用 `isolation key`（run/scenario/tenant）作用域化状态与会话（借鉴 MAF `IsolationKeyScopedAgentSessionStore` / claims-based isolation）。
- 成本配额：每租户/每实验 token 预算与熔断。
- 外部 agent/工具接入的鉴权边界（A2A 必须绑定鉴权，避免跨租户串数据）。

### B9 配置与场景工程

- 10⁵ agent 的 persona 不能手写：程序化生成（模板 + 参数分布 + 分层聚合）。
- persona 用**参数化表示**（类型、参数向量、风险偏好等），LLM 只在需要时“展开”为自然语言。
- 场景描述文件（MASim 的 `{domain}-{scenario}.md` + YAML）保持不变，扩展“规模策略”配置。

## 3. 明确的非目标（不解决）

1. LLM 底层推理加速、自研 serving、GPU 内核、量化/投机解码。
2. 自研分布式文件系统/对象存储（用现成）。
3. 自研向量数据库（用现成）。
4. 模型训练/微调/RLHF（只消费模型）。
5. 通用“超级智能体”本身（我们只搭环境与编排）。

> 把 B10 排除后，设计自由度反而更大：我们可以**假设**存在一个可横向扩展的 LLM 网关/批处理服务，专注于把“调用次数、token 量、并发、成本”这四个可控量管好。

## 4. 关键瓶颈排序（结论）

按“决定规模上限”的重要性排序：

1. **B1 决策吞吐与成本**（最硬约束）
2. **B2 通信爆炸**（第二硬约束）
3. **B4 时序/一致性 + B5 调度**（决定工程复杂度）
4. **B3 状态/内存 + B6 可靠性**（决定可运行规模与可恢复性）
5. **B7/B8/B9**（决定可运维、可治理、可规模化配置）

后续设计文档严格围绕这条排序展开：`04` 给总架构，`05/06` 解 B1 的“异构+分层”，`07` 解 B2，`08` 解 B3/B6/B8，`09` 综合解 B1/B5。
