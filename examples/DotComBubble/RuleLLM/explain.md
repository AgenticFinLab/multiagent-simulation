# DotComBubble RuleLLM — Implementation Explanation

## 1. Overview

| Item | Description |
|---|---|
| Variant | `RuleLLM` |
| Implements | `../simulation-bases.md` |
| Decision logic | LLM persona plus explicit quantitative decision guidance |
| Key difference | Unlike Rule, quantities and actions are generated by an LLM; unlike LLM, every persona receives the formulas from the shared design. |
| Research contribution | Tests whether quantitative guidance keeps language-model behavior closer to the deterministic baseline. |
| Files | `players.py`, `prompts.py`, `run_dotcombubble_rulellm.py`, `analysis.py`, `explain.md`, `analysis.md` |

The rules characterize each investor's knowledge and habits. They are prompt guidance, not a second deterministic policy that silently replaces the model output. Parsed decisions must still satisfy the canonical order schema and portfolio constraints.

## 3. Environment Mechanism Implementation

The RuleLLM variant reuses `Rule.players.Market`, which implements `simulation-bases.md §3`:

```text
P(t+1) = max(P(t) + λ·D(t) + γ·[F(t)−P(t)] + ε(t), 0.01)
```

| Symbol | Implementation/config | Value |
|---|---|---:|
| `λ` | `Market.perceive()` / `market.extras.price_impact` | `0.01` |
| `γ` | `Market.perceive()` / `market.extras.mean_reversion` | `0.005` |
| `F` | `market.extras.fundamental_value` | `100.0` |
| `σ(ε)` | `market.extras.noise_std` | `1.0` |
| `D(t)` | accepted buy volume minus sell volume | computed |

The market broadcasts `price`, `fundamental`, `deviation`, and `round`; each investor derives its own one-round price change from observed history.

## 4. RuleLLM Variant-Specific Features

Every system prompt has both required sections:

- `== PERSONA ==` describes the role and risk style.
- `== DECISION RULES ==` restates the corresponding formula from `simulation-bases.md §4`.

`RuleLLMInvestor.decide()` loads prompt paths and model settings from required config fields, calls `LangChainAPIInference`, parses `<decision>` JSON, and validates all four required fields. Malformed responses are retried at most three times and then fail explicitly. Valid quantities are capped by cash or inventory; there is no hidden hold fallback.

## 5. Architecture Diagram

```text
Market broadcast
      │
      ▼
RuleLLMInvestor.perceive() → market state + bounded price history
      │
      ▼
persona prompt + decision rules + current portfolio
      │
      ▼
LLM API → parser → schema validation → portfolio cap
      │
      ▼
canonical order → Market.perceive() in the next round
```

The star topology in `configs/DotComBubble/RuleLLM/topology.yml` connects the market bidirectionally with all five investor roles.

## 7. Running Instructions

```bash
python -m examples.DotComBubble.RuleLLM.run_dotcombubble_rulellm \
  -c configs/DotComBubble/RuleLLM/simulation.yml
```

For a bounded smoke run, add `--rounds 1`. The configured provider must have its API credentials available through `.env`. Outputs are written below `EXPERIMENT/DotComBubble/RuleLLM/`.

## 8. Expected Behavior Patterns

| Phase | Expected behavior |
|---|---|
| Early | Narrative and IPO agents supply demand; momentum waits for a move above its threshold. |
| Bubble | Momentum and narrative demand can amplify overvaluation; value and short roles supply limited resistance. |
| Correction | IPO/value/short guidance shifts as deviation crosses sell, buy, or cover thresholds. |

RuleLLM should be compared empirically with Rule and LLM. Prompt guidance is expected to improve adherence, but individual model outputs are not assumed to be deterministic.
