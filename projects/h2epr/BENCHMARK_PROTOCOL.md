# Benchmark protocol

## Construction exposure

Every event declares its exposure before package construction.

| Mode | Allowed construction material | Eligible use |
|---|---|---|
| `prefix_clean` | A declared prefix or opening-state subset | Future held-out protocol, once separately defined |
| `full_draft_exposed` | The complete Draft EPG | Architecture, workflow, and descriptive baseline development |

The current construction protocol uses `full_draft_exposed` unless an
independently approved clean-prefix protocol says otherwise. Reference EPG,
held-out data, evaluation-only content, and external research are not package
inputs, participant observations, prompts, memory, retrieval data, runtime
state, or compiler inputs. Producing a deterministic graph does not authorize
evaluation claims.

## Dataset authority

The event specification owns public event identity. The Draft owns the
benchmark-authored participant and process trajectory exposed to construction.
Frozen evidence may resolve meaning within the same dataset boundary. None of
these records becomes independently verified history merely because it is
executable.

The Source Profile records exact input hashes, transformations, aggregation,
exclusion, loss, and executable assumptions. Construction stops on an
unresolved identity or source inconsistency; it does not silently repair the
dataset.

Agent Definitions, Population Models, and Scenario Definitions cite stable
anchors in the three allowed files. They may interpret those records for
simulation but may not introduce externally researched facts. Synthetic or
sensitivity values are labeled in configuration rather than presented as
dataset observations.

## Runtime parity

Compared backends receive one backend-neutral event package and use the same
participant universe, observations, typed decision contract, environment,
clock, transport, trace, replay, and graph compiler. Decision settings belong
to backend configuration; seeds and realized source inventories belong to the
run manifest.

Backend-neutral participant products define information, authority,
admissible intents, and parameter domains. They do not encode a preferred Rule
row or LLM answer. This keeps the backend comparison substantive.

`package_sha256` establishes shared package identity. The full manifest seal,
backend binding, H2EPR runtime, and MASim event-process kernel have separate
content identities. Generated record IDs may identify evidence but may not
control priority, allocation, or any world-state effect.

## Reading and comparison levels

Generated output is considered in this order:

1. simulation-only trajectory and internal mechanics;
2. qualitative Draft-facing comparison under the declared exposure mode;
3. automated structural measures after their definitions are accepted; and
4. held-out or historical evaluation under a separately accepted clean
   protocol.

A full-Draft-exposed run can be compared descriptively with the Draft to find
implementation or modeling discrepancies. It cannot yield an unbiased
benchmark score.

Multi-run comparisons require an admitted experiment plan fixing rows, seeds,
package and binding identities, model provenance, analysis definitions, and
the complete failure denominator before execution. Admission establishes
comparison intent, not scientific validity.

## Engineering closure

Engineering closure requires:

- package, schema, hash, and backend admission;
- hash-chained trace, tick seals, and run seal;
- authoritative replay to the exact terminal state;
- one Generated EPG node for every trace record and exact trace-ID coverage;
- resolved graph endpoints and a deterministic graph seal;
- zero unresolved transport;
- two byte-identical deterministic materializations;
- generated-identity perturbation with unchanged trajectory semantics; and
- independent compact-release verification.

These properties make the generated process auditable. They do not make it
historically correct.

## Claim language

An accepted release may support statements about package validation, Rule
execution, trace integrity, replay, graph provenance, transport closure, and
deterministic repeatability. Cross-event reuse requires at least two accepted
event releases.

They do not support historical fit, parameter calibration, held-out
performance, recall or policy effectiveness, causality, scientific validity,
or universal generality. Any future claim at those levels needs an explicitly
accepted evaluation protocol and evidence boundary.
