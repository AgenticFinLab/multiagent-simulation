# Event participant batch guide

## Purpose

Individual Definitions can be locally sound yet mutually inconsistent. Batch
work establishes one event-wide participant language and makes every active
runtime decision unit traceable to one accepted human semantic parent.

## Batch ledger

Freeze and maintain one ledger with:

| Field | Why it matters |
|---|---|
| source participant and Draft anchors | proves roster completeness |
| disposition and runtime actor | exposes aggregation and exclusions |
| semantic parent path/hash | prevents machine projections from floating |
| observations produced/consumed | reveals orphan or private information |
| intents emitted/targeted | reveals missing counterparties or handlers |
| lifecycle participation | keeps pending and terminal states visible |
| state/resource authority | prevents duplicated truth |
| assumptions and limitations | distinguishes dataset support from design |

## Production sequence

1. Partition the complete roster before drafting products.
2. Define a common vocabulary for observation, intent, lifecycle, authority,
   resource, route, and result concepts.
3. Produce bounded groups that share interfaces; do not let one group invent
   vocabulary the others have not reviewed.
4. Run individual semantic review on each product.
5. Reconcile the ledger and registries after every accepted correction.
6. Run a batch review using name erasure, actor swaps, missing counterparties,
   duplicate state owners, circular observations, always-no-op activation, and
   incompatible aggregation.
7. Seal the semantic index only after every active actor and Draft anchor
   resolves.

Parallel authors may work on separate products only from the same frozen
ledger and vocabulary. Merge findings at the semantic layer before generating
registries; code is not the conflict-resolution surface.

## Reusable versus event-local feedback

An inconsistency caused by one event's vocabulary stays in the event release.
A missing product field, unclear decision rule, repeated failure class, or
schema ambiguity routes to the shared template, Skill, schema, or validator.
Record the smallest generalized example and retest it synthetically before
changing the common contract.

## Failure routing

Unaccounted source participants return to roster mapping. Misclassified
decision units return to Agent/Population ownership. World truth, route, and
effect gaps return to Scenario work. Exact values and policies remain with
configuration/backend layers. Do not close a batch by creating an actor only
in a registry or runner.

## Completion evidence

Report roster counts, disposition counts, active actor count, semantic-parent
paths and hashes, source-anchor closure, registry parity, orphan/duplicate
checks, individual verdicts, batch findings, recorded limitations, and next
legal action. There is no target actor count; completeness is relative to the
admitted Draft and selected process window.
