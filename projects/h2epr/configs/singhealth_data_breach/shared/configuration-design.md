# SingHealth Data Breach Scenario Configuration

## Identity and purpose

Shared configuration `h2epr.0616.comparison.v1` selects one dataset-conditioned
incident-response process; `h2epr.0616.rule.v1` owns deterministic participant
choices. It is a reproducibility baseline, not an intrusion reconstruction,
historical fit, security policy or admitted scientific experiment.

## Exact parent boundary

The assembly pins the Source Profile, complete roster/map, eight human parents,
participant interface, Scenario and configuration releases. Maintained
declarative environment/annotation implementations own effects. The Rule
realization pins common source hashes; no event-specific runtime Python or MASim
change is present.

## Rule settings and behavioral use

The Rule configuration contains 17 ordered rows with inclusive windows, explicit
state and delivered-message guards, one-action-per-actor cadence and `no_op`
fallback. Accepted rows complete once. Unchanged rejection does not trigger a
retry; later delivered information may reopen a still-available row.

The selected values are record labels and qualified messages. No exploit
probability, detection rate, disclosure utility, penalty response, remediation
effect or attribution confidence is estimated. Alternative behavior requires a
semantic-parent successor before backend tuning.

## Variants, verification, and failure routing

Construction variants withhold scope verification or delay findings through
freshly admitted configuration/package successors. They may publish with open
expected fields when trace, seals, replay, graph and transport close. They are
mechanism probes, not cross-backend experiments or counterfactual policy claims.

Schema, provenance, source, release, actor, intent, route or hash mismatch fails
admission. Runtime rejection changes no state and preserves its disposition.
Unresolved transport or replay/graph/rematerialization mismatch blocks release.
