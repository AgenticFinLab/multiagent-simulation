# TikTok dispute Scenario Configuration

## Identity and purpose

Shared configuration `h2epr.0170.comparison.v1` selects one dataset-conditioned
public-record process; `h2epr.0170.rule.v1` owns deterministic participant choices.
It is a reproducibility baseline, not a legal, platform, security, speech,
market or negotiation-effectiveness model.

## Exact parent boundary

The assembly pins the Source Profile, full roster/map, ten human parents,
interfaces, Scenario and configuration releases. Common declarative environment
and annotation implementations own effects. No event-specific runtime Python,
model/network access or MASim modification exists.

## Rule settings and behavioral use

The Rule configuration contains 23 ordered rows with inclusive windows, state
or delivered-message guards, one action per actor/coordinate and `no_op`
fallback. Accepted rows finish once; unchanged rejection does not reopen them.

Values are qualified public/organizational records. No threat probability,
legal judgment, speech effect, user response, valuation, data transfer,
algorithm control or negotiation utility is estimated.

## Variants, verification, and failure routing

Construction variants suppress testimony through an impossible-in-window
receipt guard or delay the ByteDance-to-judiciary appeal route. Open expected
fields can publish only when trace, seals, replay, graph and transport close.
These are mechanism probes, not historical counterfactuals.

Schema, provenance, source, actor, intent, route or hash mismatch fails
admission. Runtime rejection changes no state. Unresolved transport or
replay/graph/rematerialization mismatch blocks release.
